# WebSphere Application Server — CloneIDs & JSESSIONID Sticky Sessions Explained

## Overview

This document explains how **CloneIDs** and the **JSESSIONID cookie** work together in IBM WebSphere Application Server (WAS) to enable **sticky session affinity** in a clustered environment behind IBM HTTP Server (IHS).

| Analogy (Bank)      | WebSphere Equivalent        |
|---------------------|-----------------------------|
| Teller              | JVM (application server)    |
| Papers on teller's desk | Session data in JVM memory |
| Teller badge number | CloneID                     |
| Token slip with badge number | JSESSIONID cookie  |

---

## What is a CloneID?

A **CloneID** is a short unique identifier ("badge number") assigned by WAS to each JVM in a cluster. It is stored in `plugin-cfg.xml` on the IHS (web server) machine.

### Example `plugin-cfg.xml` entries

```xml
<Server Name="was1_PaymentCluster_server1" CloneID="1a2b3c" .../>
<Server Name="was2_PaymentCluster_server1" CloneID="4d5e6f" .../>
<Server Name="was3_PaymentCluster_server1" CloneID="7g8h9i" .../>
<Server Name="was4_PaymentCluster_server1" CloneID="ab1cd2" .../>
```

### Rules

- No two JVMs can ever share the same CloneID.
- CloneIDs are **generated by WAS itself** — never invent them.
- CloneIDs remain stable as long as the server profile exists (they change only if the profile is recreated).

---

## What is JSESSIONID?

The **JSESSIONID** is an HTTP cookie issued by the server at login. The browser stores it and sends it with every subsequent request.

### Structure

```
JSESSIONID = 0000r8KG7dLM9Xpq4vNZ2wTR : 7g8h9i
             ├────── Session ID ──────┤ ├─ CloneID ─┤
             (WHO you are — JVM reads)   (WHERE your session
                                          lives — Plugin reads)
```

| Part (relative to `:`) | Meaning             | Consumer |
|------------------------|---------------------|----------|
| Left side              | Random unique session ID — locates session data in JVM memory | The JVM |
| Right side             | CloneID — locates which JVM holds the session | The Plugin |

> [!TIP]
> Memorize it as: **JSESSIONID = WHO_YOU_ARE : WHERE_YOUR_SESSION_LIVES**

### Sample cookie

```
Set-Cookie: JSESSIONID=0000r8KG7dLM9Xpq4vNZ2wTR:7g8h9i; Path=/NetBanking; Secure; HttpOnly
```

## End-to-End Flow Example

Scenario: A user (`Ravi`) logs into a net-banking app served by a 4-JVM cluster.

### Request 1 — Open login page

1. IHS receives `GET /NetBanking/login`.
2. Plugin checks for a JSESSIONID cookie → **none** (first visit).
3. No cookie → Round Robin → picks JVM2.
4. Login page served. No session created yet.

> [!NOTE]
> Viewing a page does not create a session. **Logging in creates the session.**

### Request 2 — Submit credentials

1. Plugin still sees no cookie → Round Robin → picks JVM3.
2. JVM3 validates credentials and creates a session in its own memory.
3. JVM3 generates a session ID (`0000r8KG7dLM9Xpq4vNZ2wTR`) and stamps its own CloneID (`7g8h9i`) into the cookie.
4. Browser stores the JSESSIONID cookie.

### Request 3 — Click "Fund Transfer"

1. Plugin reads the cookie and extracts the CloneID after the `:` → `7g8h9i`.
2. Plugin matches `7g8h9i` in `plugin-cfg.xml` → `was3_PaymentCluster_server1`.
3. Request routed to JVM3 — **Round Robin is skipped**.
4. JVM3 finds Ravi's session in memory and serves the page.

Requests 4 and 5 repeat the same pattern: Plugin reads CloneID → JVM3 → JVM3 → JVM3. This is a **sticky session**.

## Plugin Routing Decision Tree

```
New request arrives
        │
        ▼
Is there a JSESSIONID cookie?
        │
   NO ─┴─ pick any JVM (new visitor)
        │
   YES
        ▼
Extract CloneID after ":"
        │
        ▼
Find that CloneID in plugin-cfg.xml
        │
        ├── FOUND + server UP    → Route there ✅ (sticky works)
        │
        ├── FOUND + server DOWN  → Round Robin fallback
        │                          (session lost, unless replication)
        │
        └── NOT FOUND            → Round Robin to any JVM
                                   (session lost — CloneID mismatch!)
```

## When Does Session Affinity Break?

### Scenario A — JVM crashes mid-transaction

- Plugin routes to the CloneID's JVM, but the JVM is **dead**.
- Plugin falls back to Round Robin → user's session is gone → forced re-login; in-flight transaction is lost.

**Fix:** Memory-to-Memory Session Replication — sessions are copied to peer JVMs in the cluster, so a surviving JVM can resume the session.

### Scenario B — Duplicate CloneID

- Cloning a WAS profile carelessly produces two JVMs with the same CloneID.
- Plugin randomly picks either JVM → ~50% of requests hit a JVM with no session → random logouts.

**Fix:** CloneIDs must be unique. Correct the CloneID on the offending server.

### Scenario C — Cookies disabled in browser

- No cookie → Plugin falls back to **URL rewriting**:

```
/NetBanking/fundtransfer;jsessionid=0000r8KG7dLM9Xpq4vNZ2wTR7g8h9i
```

- The plugin reads `AffinityURLIdentifier="jsessionid"` from `plugin-cfg.xml` and extracts affinity info from the URL.
- Drawbacks: ugly URLs and session ID leakage into bookmarks/logs.

> [!NOTE]
> Banking environments typically force cookies (`Secure`, `HttpOnly`) and disable URL rewriting.

### Scenario D — CloneID changed after plugin regeneration

- A profile change alters the CloneID (`7g8h9i` → `zz9988`), and `plugin-cfg.xml` is regenerated.
- Browsers still hold the **old** cookie with `7g8h9i` → lookup fails → Round Robin → mass random logouts after every deploy.

**Fix:** CloneIDs are stable by design and change only if a profile is recreated. If mass logout complaints appear right after plugin regeneration, **check for CloneID mismatch first**.

## Quick Reference Card

| Concept            | One-Line Meaning                                                             |
|--------------------|------------------------------------------------------------------------------|
| CloneID            | Unique badge number of a JVM, lives in `plugin-cfg.xml`                       |
| JSESSIONID         | Cookie = `SessionID : CloneID` |
| `:` separator      | Left = who you are (JVM reads) / Right = where your session lives (Plugin reads) |
| Sticky session     | Plugin routes every request to the same JVM using the CloneID                 |
| Round Robin        | Fallback when no cookie exists or the CloneID can't be matched                |
| Session creation   | Happens when the user **logs in** — not when viewing the login page           |
| Replication        | The fix for "JVM died mid-transaction"                                        |
| URL rewriting      | The fallback when cookies are disabled (rare in banks)                        |
